# 组队登记校验、冲突确认与通知

Status: ready-for-agent

## Problem Statement

队长通过组队收集表提交队伍信息后，需要自动判断队伍是否符合活动规则，并在成功或普通失败时通知相关人员。当新登记与已有预组队信息发生成员重叠、换队长或其他结构性冲突时，不能直接覆盖原队伍，需要通知管理员人工确认。

## Solution

完善组队收集表、导入校验和通知流程：

- 表单收集队长信息、队友人数和对应数量的队友信息。
- 队伍总人数必须为 3–5 人。
- 所有成员必须能按归一化手机号匹配选手表。
- 队伍至少包含一名 `年级 = 大一` 的成员。
- 所有成员必须满足 `验证状态 = 已验证`；该状态作为已入群判断。
- 同一成员只能属于一个队伍。
- 普通校验失败仍通知队长失败原因；队长没有可用 `open_id` 时才按既定规则降级到第一个可用队友。
- 校验成功后只通知队长“完成验证、组队成功”。
- 新组队登记提交后自动触发判断；已经判断过的登记不得重复判断、重复通知或重复写入。
- 与已有预组队或队伍信息发生结构性冲突时，标记为“需管理员确认”，不自动创建新队伍、不自动更新原队伍。
- 出现待人工确认的组队登记时，向配置文件中指定的管理员 `open_id` 发送冲突详情。
- 管理员同意后，机器人自动重新读取最新数据并执行对应处理，处理成功后更新登记状态并通知相关人员。

## User Stories

1. 作为队长，我希望填写队友人数，以便系统知道应收集多少名队友。
2. 作为队长，我希望只看到与队友人数对应的填写问题，以减少无关字段。
3. 作为队长，我希望队伍总人数必须为 3–5 人。
4. 作为队长，我希望队伍至少有一名大一新生。
5. 作为队长，我希望所有队员都完成验证后才能组队成功。
6. 作为队长，我希望手机号无法匹配选手表时收到具体失败原因。
7. 作为队长，我希望普通校验失败仍能收到机器人失败通知。
8. 作为队长，我希望校验全部通过后收到“完成验证”和“组队成功”通知。
9. 作为系统管理员，我希望队长没有可用身份时，失败通知能发送给第一个可用队友。
10. 作为系统管理员，我希望成功通知只发送给队长，不重复通知队友。
11. 作为系统管理员，我希望新登记与已有队伍完全一致时识别为重复或无需变更。
12. 作为系统管理员，我希望原队伍只新增成员时识别为潜在增员场景。
13. 作为系统管理员，我希望换队长、替换成员、减少成员或跨队重叠时识别为结构性冲突。
14. 作为系统管理员，我希望冲突登记进入“需管理员确认”状态，而不是自动覆盖原队伍。
15. 作为指定管理员，我希望收到登记记录 ID、原队伍、新提交成员和冲突类型。
16. 作为系统管理员，我希望普通校验失败通知队长，结构性冲突通知管理员。
17. 作为系统管理员，我希望待确认登记不会创建重复队伍。
18. 作为系统管理员，我希望没有可用收件人时仍保留导入结果和通知失败原因。
19. 作为系统管理员，我希望重复运行导入脚本不会重复创建队伍或重复处理已完成登记。
20. 作为系统管理员，我希望新登记提交后自动触发判断，不需要手动启动导入。
21. 作为系统管理员，我希望已经判断过的登记不会重复校验、重复通知或重复写入。
22. 作为指定管理员，我希望确认冲突登记后机器人自动执行队伍处理。
23. 作为系统管理员，我希望管理员确认后的处理使用最新选手表和队伍表状态。
24. 作为系统管理员，我希望管理员确认处理成功后登记状态、队伍数据和通知结果保持一致。
25. 作为系统管理员，我希望管理员通知对象通过配置文件维护，而不是硬编码在业务逻辑中。

## Implementation Decisions

- 以现有组队收集表和导入脚本作为主处理入口。
- 使用归一化手机号匹配选手表，并使用现有队伍成员关系判断一人一队。
- 资格校验顺序为：字段完整性 → 手机号格式 → 队友人数一致性 → 总人数 3–5 → 选手表匹配 → 一人一队 → 至少一名大一 → 全员已验证。
- `验证状态 = 已验证` 是本需求指定的入群判断依据，不额外调用群成员 API。
- 普通校验失败仍发送队长结果通知；成功通知只发送给队长，通知逻辑不因管理员通知需求改变。
- 结构性冲突至少包括：队长变更、成员替换、成员减少、一个登记匹配多个已有队伍、登记成员来自多个已有队伍、无法唯一匹配原队伍。
- 结构性冲突状态为“需管理员确认”；确认前不创建新队伍、不更新原队伍、不删除原成员。
- 新登记自动判断必须具备幂等标识和状态闸门；已处于已判断、已导入、已跳过或待确认状态的登记不得被普通扫描重复处理。
- 管理员确认后的处理必须重新读取最新选手表、队伍表和登记记录，避免基于过期快照写入。
- 管理员确认动作必须幂等；同一登记重复确认不得重复创建队伍、重复更新队伍或重复发送成功通知。
- 管理员通知目标从配置文件读取，默认配置值为 `ou_37995518aa74b508e6a7b67db7151692`；业务代码不得硬编码该身份。
- 管理员通知内容包含登记记录 ID、冲突类型、原队伍 ID、原成员、新提交队长和新提交成员。
- 普通校验失败仍通知队长；结构性冲突通知管理员，不能用管理员通知替代队长失败通知。
- 管理员通知失败不能改变冲突状态，应将失败原因记录到导入结果。
- 保留现有导入状态、导入结果和来源记录机制。
- 管理员确认后自动执行本次冲突对应的队伍处理；处理前重新读取最新数据，处理过程必须幂等。
- 表单动态显示仍需通过飞书表单编辑界面的条件逻辑配置；开放 API 不支持时，不以静态隐藏字段冒充动态联动。

## Testing Decisions

- 测试总人数为 2、3、4、5、6 时，只有 3–5 通过。
- 测试至少一名大一、无大一、存在未验证成员、手机号未匹配选手表等资格边界。
- 测试成员已属于其他队伍时，普通失败通知仍发送给队长或既定队友兜底收件人。
- 测试队长有可用 `open_id` 时只发送给队长；队长无可用 `open_id` 时只发送给第一个可用队友。
- 测试普通失败消息包含具体失败原因。
- 测试已有队伍完全一致、仅新增成员、换队长、替换成员、减少成员、跨队重叠和多队匹配的分类结果。
- 测试结构性冲突只通知指定管理员，不创建或更新队伍。
- 测试管理员通知失败仍保留待确认状态和错误信息。
- 测试重复运行不会重复判断、重复发送或重复创建。
- 测试新登记自动触发判断，并验证已判断登记被幂等跳过。
- 测试管理员确认后自动处理，且重复确认不会重复处理。
- 测试管理员 `open_id` 从配置文件读取，修改配置即可更换通知对象。
- dry-run 只读取并报告，不发送任何参赛者或管理员消息，也不写入数据。
- 测试 seam 以现有导入处理、队伍/选手仓库和机器人文本消息发送接口为主，验证外部行为而非私有实现细节。

## Out of Scope

- 不实现未被规格定义的其他管理员审批流程；本规格只覆盖组队登记冲突的确认和自动处理。
- 不通过群成员 API 判断真实入群状态。
- 不自动补录未验证选手。
- 不自动删除原成员或覆盖预组队信息。
- 不向所有队友群发成功/失败消息。
- 不新增独立 Web 表单或替换飞书多维表格。
- 不保证点击表单提交后立即触发处理。
- 不修改管理员现有手动加队友指令。

## Further Notes

- “普通失败”是当前提交自身不满足资格的失败，例如人数、年级、验证状态、手机号和一人一队。
- “需管理员确认”是涉及已有队伍归属或成员结构的冲突，必须先通知管理员并阻断自动写入。
- 当前管理员 `open_id` 是用户明确提供的固定值；未来如需变更，应改为配置项或管理员名单。
